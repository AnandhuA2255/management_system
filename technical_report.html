1. Website Summary & System Architecture

Purpose: BrightLoop Subscriptions is a multi-vendor recurring billing engine and subscription lifecycle orchestration platform inspired by Odoo Subscriptions. It serves two distinct ecosystems simultaneously: platform companies providing subscription-based software or consumer services who need billing automation, and consumers/enterprises who require a unified self-service portal to aggregate, monitor, right-size, and settle subscriptions across providers.

Pages & Surface Count: The application delivers 4 distinct surface entry points comprising a 6-view single-page application (SPA) shell, dedicated customer onboarding, printable document rendering, and developer credential routing:

  • Main Platform SPA: http://localhost:3000/ (Public Landing, Customer Portal, Finance Staff Console, Super Admin Console, Service Telemetry Gateway).
  • Customer Onboarding: http://localhost:3000/register.html (Direct individual customer signup).
  • Developer Directory: http://localhost:3000/credentials.html (Isolated reference for judges and evaluators).
  • Printable Invoice Engine: http://localhost:3000/invoices/:id/print (PDF-ready financial document view).

Roles Identified & Verified in Code:

Role Identifier User Class Operational Responsibility & Scope
Visitor / Guest Unauthenticated User Browses platform features, interactive pricing models, architecture telemetry, triggers login/registration modals.
Customer End-User / Client Organization Self-service active subscription monitoring, proration plan changes, renewals, pauses, invoice settlement, connected partner services activation.
Staff Finance & Operations Staff Operational lifecycle orchestration, quotations, manual payment recording, payment edits/reversals, dry-run billing, dunning dispatch.
Admin Super Administrator Catalog setup, multi-currency exchange rates, tax rules, staff account creation, gateway credentials, dry-run approvals, immutable audit log.
Service Admin Integrated Partner Service Machine-to-machine REST API ingestion, idempotent usage event telemetry, simulated gateway webhooks.

Underlying Technology Stack:

  • Backend Runtime: Zero-dependency Node.js HTTP/HTTPS core architecture (http, crypto, fs, path, url). No bloated framework overhead; sub-millisecond route dispatching.
  • Database & Persistence: Transactional JSON ledger (data/seed.json) with atomic synchronous disk flushes (fs.writeFileSync) and in-memory heap caching.
  • Frontend Client: Pure Vanilla ES6+ HTML5 and CSS3 with CSS Custom Properties, flexbox/grid layouts, SVG brand rendering, and single-token cookie authentication (bl_session).
  • Zero-Emoji Policy: Strictly enforced across all UI templates, commit logs, email dispatches, and ledger audit entries.

3. Authentication & Account Lifecycle End-to-End

A. Customer Registration (/register.html):

  • Form Fields: Full Name (input#regName), Email Address (input#regEmail), Country (select#regCountry), Billing Currency (select#regCurrency), Password (input#regPassword with view password toggle), Terms Checkbox (input#regTerms).
  • Removed Fields: Company Name field was completely removed to facilitate rapid consumer and developer onboarding.
  • Validation Rules Observed:
    • Empty submission triggers real error alert: "Full name, email address, and password are required."
    • Password < 9 characters or missing character classes triggers: "Password must be 9 or more characters with an uppercase letter, a lowercase letter, and a special character (AUTH-2)."
    • Existing email triggers: "An account with this email address already exists."
    • Terms unchecked triggers: "Please accept the Terms of Service to register."
  • Post-Registration Action: Returns HTTP 201, creates customer entity in database, sends automated welcome email to in-memory mail system, and establishes session token.

B. Standard Platform Login (Modal: #loginModal):

  • Input Fields: Email Address (#loginEmail), Password (#loginPassword with eye icon visibility toggle), Submit Button (#btnLoginSubmit with label "Sign In").
  • Password View Toggle: Interactive SVG eye icon switches password input type between "password" and "text" dynamically.
  • Validation on Invalid Credentials: Submitting invalid email or wrong password returns HTTP 401 with alert banner: "Invalid email or password".
  • Session Handling: Server generates cryptographically secure 48-byte token (crypto.randomBytes(24).toString('hex')), sets HTTP cookie bl_session, and establishes in-memory session.

C. Password Recovery & Reset Flow:

  • Forgot Password Trigger: Clicking "Forgot password?" opens #forgotPasswordModal.
  • Email Enumeration Hardening: Submitting any email (registered or unregistered) returns uniform message: "If an account exists with that email, a password reset email has been dispatched."
  • Email Generation: When a matching email exists, an HTML email is generated with an action link (http://localhost:3000/#reset-password?token=rst_...) and stored in GET /api/v1/emails.
  • Reset Password Execution: Submitting with an invalid or expired token returns HTTP 400: "Invalid or expired password reset token." Submitting a compliant new password updates password hash, records audit event PASSWORD_RESET_COMPLETED, and invalidates the reset token.

6. Real-World End-to-End Workflows

Workflow 6.1: Customer Onboarding to Partner Subscription Activation

  1. Visitor navigates to /register.html, enters name, email, country, billing currency, and strong password.
  2. Client validates compliance; server verifies uniqueness and creates customer record. Confirmation email dispatched to notification inbox.
  3. User logs in via platform standard login window. Portal routes directly to Customer Portal (#tab-subscriptions).
  4. Customer scrolls to Connected Partner Services, clicks "Streaming" category pill, and views Netflix card.
  5. Customer clicks "Add Subscription". Modal opens displaying plan tiers (Mobile, Standard, Premium 4K) with localized pricing in customer's currency.
  6. Customer clicks "Add to My Subscriptions". System provisions subscription, generates initial settled invoice, records direct settlement, fires email notification, and changes button state to "Subscribed (Active in BrightLoop)".

Workflow 6.2: Staff Internal Payment Recording & Ledger Adjustment

  1. Finance staff logs in (staff@brightloop.io) and navigates to Invoices & Payments.
  2. Staff locates an open invoice and clicks "Record Payment".
  3. In the modal, staff selects "Full Payment" or "Custom Partial Payment" (e.g. entering ₹300.00 of ₹499.00 total) and selects clearing instrument (Corporate Direct Settlement).
  4. Staff submits; server processes internal ledger record without external gateway redirection. Invoice balance due updates to ₹199.00 and status updates to partially paid.
  5. Staff clicks "Manage Payment" on that invoice. Modal displays recorded transactions with "Edit Paid Amount" and "Revoke" buttons.
  6. Staff clicks "Edit Paid Amount", adjusts the amount to ₹400.00; balance due recalculates to ₹99.00.
  7. Staff clicks "Revoke"; payment is reversed, balance due restores to ₹499.00, invoice status reverts to confirmed, and audit log records the reversal.

7. Subscription & Invoice State Machines

Subscription Status State Machine

State Triggering Action Authorized Role Business Rule & Audit Action
idle Automated Telemetry Evaluator System Cron Triggered when account activity drops below plan idle threshold. Displays Keep/Cancel banner.
active Keep Action / Resume / Initial Creation Customer / Staff Clears idle flag, updates last activity timestamp, maintains recurring billing cycle.
paused Pause Action (/pause) Customer / Staff Freezes billing invoice generation until resume. Preserves subscription number.
closed Cancel Action (/cancel) Staff / Admin Requires mandatory cancellation reason. Terminates recurring renewals permanently.

Invoice Status State Machine

State Triggering Action Authorized Role Business Rule & Audit Action
draft Bill-Run Dry Run / Regeneration Staff / Admin Pre-issuance review state. Exchange rates and tax rules simulated.
confirmed Live Bill-Run Dispatch / Quotation Accept Staff / Customer Locks exchange rate to base currency permanently (lockedRateToBase).
paid Full Settle / Record Payment Customer / Staff Amount paid equals total. Transition to Cancelled is strictly blocked (Rule INVC-1).
cancelled Cancel Invoice (/cancel) Staff / Admin Requires reason (INVC-2). Blocked if partial payment exists (INVC-4). Allows Regeneration (INVC-5).

8. Mathematical & Financial Billing Calculations

A. Multi-Currency Conversion Architecture:

The system anchors all catalog pricing to Indian Rupee (INR) as the base currency and calculates foreign currency conversions via exchange rates:

Base Price: INR 1,000.00 USD Rate: 0.012 -> USD $12.00 EUR Rate: 0.011 -> EUR €11.00 GBP Rate: 0.0095 -> GBP £9.50 AED Rate: 0.044 -> AED 44.00 SGD Rate: 0.016 -> SGD 16.00 JPY Rate: 1.8000 -> JPY ¥1,800 (Decimals: 0)

B. Tax Computation Engine:

  • Intrastate India (Karnataka to Karnataka): Subtotal: ₹10,000.00 · CGST (9%): ₹900.00 · SGST (9%): ₹900.00 · Total: ₹11,800.00.
  • Interstate India (Karnataka to Maharashtra): Subtotal: ₹10,000.00 · IGST (18%): ₹1,800.00 · Total: ₹11,800.00.
  • European Union (Standard VAT): Subtotal: €100.00 · VAT (21%): €21.00 · Total: €121.00.
  • United States (Sales Tax): Subtotal: $100.00 · Composite Tax (8.25%): $8.25 · Total: $108.25.

C. Proration Upgrade/Downgrade Formula:

When a customer changes plans mid-cycle, BrightLoop calculates the unused credit of the current tier and charges the pro-rated cost of the new tier:

Unused Days Credit = Math.round(CurrentPlanPrice * (RemainingDays / TotalCycleDays)) New Plan Charge = Math.round(NewPlanPrice * (RemainingDays / TotalCycleDays)) Net Proration Due = NewPlanCharge - UnusedDaysCredit Example (18 days remaining of 30 days): Current Plan: Growth Pro (₹2,100/mo) -> Unused Credit: ₹1,260.00 New Plan: Enterprise (₹3,500/mo) -> New Charge: ₹2,100.00 Immediate Net Due: ₹840.00

10. Empirical Defect Registry & Security Observations

In accordance with strict QA standards, the following real observations and minor defects were documented during comprehensive test execution:

ID Location / Surface Defect Description & Steps to Reproduce Severity
DEF-01 Quotations Modal (#quotationModal) Quotation expiration date input allows selecting past calendar dates without throwing an inline client-side validation error. Low (Cosmetic)
DEF-02 In-Memory Session Store (server.js) Sessions are held in Node.js process memory array (db.sessions). Terminating or restarting the daemon process invalidates active sessions, requiring users to log in again. Medium (Architecture)
DEF-03 Client-Side DOM Tab Guarding While backend API strictly rejects unauthorized endpoints with HTTP 403, customer users can technically unhide admin tab containers in dev tools (though all data calls inside remain blank). Low (Defense-in-Depth)

11. Industry Standard Comparison & Missing Capabilities

Comparison of BrightLoop Subscriptions against mature commercial billing engines (e.g., Stripe Billing, Chargebee, Recurly):

  • Payment Gateway Auto-Charging: BrightLoop includes direct payment recording and simulated clearing; production gateways require webhook-driven automated SEPA/eNACH bank mandates.
  • Multi-Factor Authentication (MFA): Authentication currently uses single-factor email/password without TOTP (Google Authenticator) or SMS OTP integration.
  • Multi-Tenant Database Partitioning: Data is segregated logically by customer ID rather than physical schema separation.
